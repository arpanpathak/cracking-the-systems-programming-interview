Distributed Systems from the Ground Up

Key-Value Store: Replication (Low-Level Design)

The storage node of chapter 2 keeps every acknowledged write when its process crashes. Against the loss of the machine itself, or of its disk, it offers nothing: a log on 1 disk is gone when that disk is gone. Non-functional requirement 0 of chapter 1 demands that an acknowledged write survive the loss of any 1 machine, and it follows that the record of every write has to be stored on at least 2 machines before the client is answered.

To copy a file from 1 machine to another is easy. What makes replication a subject is that the copying takes place over a network which loses messages, delays them and delivers their answers late or not at all, between machines that stop and restart at arbitrary moments, and that through all of this the copies must remain identical, in content and in order, record for record. A follower that has missed a message must not apply the next one as though nothing were missing. A leader that has lost an answer must not conclude that the follower lacks the record, nor that it has it. And a machine that was the leader an hour ago and has since been replaced must be prevented from writing as though it still were.

This chapter implements the replication that chapter 1 specified: a leader that orders the writes of a shard, and 2 followers that store the same records in the same order. It turns out that a single small rule on the follower’s side handles every one of the situations listed above. We define the messages and the state of a replica, derive the rules for followers and leaders, and implement them as a library that performs no network operations whatever, so that a simulation can subject it to every possible combination of lost messages. We then build kvnode, a storage node that exchanges the messages over gRPC, and run 3 nodes while stopping followers, removing the majority, and replacing a lost leader.

Overview

Every shard has 3 replicas. All writes go to the leader, and the other 2 replicas are followers. Figure 3.1 shows the nodes of this chapter and the route of a write among them.

The implementation maintains 4 invariants.

  1. The log of every follower is a prefix of its leader’s log: the same records in the same order, and possibly fewer of them.
  2. A record is acknowledged to its client only after at least 2 of the 3 logs hold it.
  3. A replica applies a record to its entries only after the record is known to be held in at least 2 of the 3 logs.
  4. A replica rejects every message from a leader whose term is lower than its own.

The second invariant is non-functional requirement 0 in the form of a rule. The third ensures that a read returns only data which would survive the loss of a machine. The fourth prevents a former leader from modifying a shard after it has been replaced.

In this chapter the leader of a shard is chosen by an operator, who starts 1 node in that role. Automatic election, as chapter 1 described it, is built upon the mechanism of this chapter and is the subject of chapter 4.

The messages

The protocol of chapter 1 defines a single call, Append, which a leader sends to each of its followers.

Listing 3.1 The replication service in the schema. proto/store.proto

// Sent by the leader of a shard to each follower.
service Replication {
  // Appends records to the follower's log. A call with no records is a
  // heartbeat: it tells the follower that the leader is alive.
  rpc Append(AppendRequest) returns (AppendResponse);
}

message AppendRequest {
  // The shard, named by the last position it owns.
  fixed64 shard = 1;
  // The term of the sender. A follower rejects a leader of an older term.
  uint64 term = 2;
  // The sequence of the record that precedes `records` in the leader's log.
  uint64 previous_sequence = 3;
  repeated Record records = 4;
  // Every record up to this sequence is on a majority of the replicas.
  uint64 committed_sequence = 5;
  // Added for leader election. The term of the record at previous_sequence,
  // and the id of the sender.
  uint64 previous_term = 6;
  uint32 leader = 7;
}

message AppendResponse {
  uint64 term = 1;
  // False when the follower's log does not end at `previous_sequence`.
  bool appended = 2;
  // The sequence of the last record in the follower's log.
  uint64 last_sequence = 3;
}

The library uses types of its own for these messages, so that it has no dependence on gRPC, and the conversion between the 2 representations is performed in the node.

The last field is the one on which the whole protocol turns. A follower never merely says yes or no. In every answer it reports where its log now ends, and this single number is enough for a leader to correct any mistaken belief it may hold about that follower.

The state of a replica

A replica consists of a log, of the entries that result from applying a part of that log, and of 3 numbers: the sequence of its last record, the point up to which records have been applied, and its term.

A record is committed when a majority of the replicas has stored it. A committed record survives the loss of any 1 machine, since any 2 of the 3 replicas include at least 1 that holds it. A replica keeps uncommitted records in its log without applying them. The entries therefore reflect committed records only, and no read can return a value that might yet be lost.

Figure 3.3 shows where each part of this state resides and which operation carries data from 1 part to another.

In the code, records is a vector that holds record n at index n - 1, so that its length is the sequence of its last record. commit proceeds from committed to the sequence it is given and passes each record to apply, the function of chapter 2 that inserts or removes an entry. Since commit is the only caller of apply, there is no path by which an uncommitted record can reach the entries.

pub struct Replica {
    log: Log,
    /// Every record of the log, in order. Record `n` is at index `n - 1`.
    records: Vec<Record>,
    /// The result of applying the records up to `committed`.
    entries: BTreeMap<String, Entry>,
    /// The sequence of the last record that is applied to `entries`.
    committed: u64,
    term: u64,
}

impl Replica {
    /// Opens the replica in `directory`. Nothing is applied yet: a replica
    /// that has restarted does not know which of its records are committed.
    pub fn open(directory: &Path, sync: bool, term: u64) -> io::Result<Replica> {
        let (log, recovery) = Log::open(directory, sync)?;

        Ok(Replica {
            log,
            records: recovery.records,
            entries: BTreeMap::new(),
            committed: 0,
            term,
        })
    }

    pub fn term(&self) -> u64 {
        self.term
    }

    pub fn last_sequence(&self) -> u64 {
        self.records.len() as u64
    }

    pub fn committed(&self) -> u64 {
        self.committed
    }

    /// One page of the committed keys.
    pub fn list(&self, prefix: &str, after: Option<&str>, limit: usize) -> (Vec<Summary>, bool) {
        page(&self.entries, prefix, after, limit)
    }

    /// Every record of the log, in order.
    pub fn records(&self) -> &[Record] {
        &self.records
    }

    /// The committed value of a key.
    pub fn get(&self, key: &str) -> Option<&Entry> {
        self.entries.get(key)
    }

    /// Applies the records up to `sequence` that are not applied yet.
    pub fn commit(&mut self, sequence: u64) {
        let until = sequence.min(self.last_sequence());

        while self.committed < until {
            apply(
                &mut self.entries,
                self.records[self.committed as usize].clone(),
            );
            self.committed += 1;
        }
    }
}

Replica::open sets committed to 0 and leaves the entries empty, although the log may contain records. This may seem wasteful, and it is in fact necessary. After a restart, a replica cannot tell from its own log which of its records had reached a majority, since its last few records may exist on its own disk and nowhere else. A follower learns the committed sequence from its leader, and a leader learns it from the answers of its followers.

The follower

A follower applies the same procedure to every message it receives.

ConditionActionAnswer
The term of the message is lower than the follower’s own.noneappended = false, with the follower’s term
previous_sequence differs from the end of the follower’s log.adopt the termappended = false, with the end of the follower’s log
previous_sequence equals the end of the follower’s log.adopt the term, append the records with 1 wait for the disk, apply records up to committed_sequenceappended = true, with the new end of the log

handle_append is a direct transcription of that figure. Each check that fails returns by way of a closure named refuse, which builds an answer from the follower’s present term and the end of its log. When both checks pass, append_records writes the whole batch with a single wait for the disk, and commit then applies whatever the leader has declared committed. Since commit stops at the end of the log, a committed sequence that lies beyond what this follower holds does no harm.

Listing 3.5 The follower's handling of a message. repl/src/lib.rs

impl Replica {
    /// Processes a message from a leader.
    pub fn handle_append(&mut self, request: Append) -> io::Result<Appended> {
        let refuse = |replica: &Replica| Appended {
            term: replica.term,
            appended: false,
            last_sequence: replica.last_sequence(),
        };

        if request.term < self.term {
            return Ok(refuse(self));
        }

        self.term = request.term;

        if request.previous_sequence != self.last_sequence() {
            return Ok(refuse(self));
        }

        if !request.records.is_empty() {
            self.log
                .append_records(&request.records)?;
            self.records.extend(request.records);
        }

        self.commit(request.committed_sequence);

        Ok(Appended {
            term: self.term,
            appended: true,
            last_sequence: self.last_sequence(),
        })
    }
}

The second row of the table is what maintains invariant 1, and it deserves to be looked at closely, since the whole reliability of replication derives from it. A follower appends records only at the exact position where the leader’s message begins. Its log can therefore never acquire a gap, a duplicate or a record out of place, whatever has happened to earlier messages. When the positions differ, the follower attempts no repair of any kind. It reports where its log ends, and the leader sends a message that begins there.

This 1 exchange covers every circumstance in which a follower is behind or the leader’s information is out of date: a follower that was stopped and has restarted, a message that was lost, an answer that was lost, and a new follower with an empty log. None of these cases has code of its own. They are all the same case, in which the leader’s belief about the end of the follower’s log is wrong and the follower’s answer puts it right.

The records of a message are appended with Log::append_records, which writes all of them and waits for the disk once.

Listing 3.7 Appending a batch of records that another node has numbered. kv/src/log.rs

impl Log {
    /// Appends records that another node numbered, in one write and with one
    /// wait for the disk. The first record must follow the last record of
    /// this log.
    pub fn append_records(&mut self, records: &[Record]) -> io::Result<()> {
        if self.failed {
            return Err(io::Error::other(
                "the log failed on an earlier write and is closed",
            ));
        }

        let misplaced = (self.next..)
            .zip(records)
            .find(|(expected, record)| record.sequence != *expected);

        if let Some((expected, record)) = misplaced {
            return Err(io::Error::other(format!(
                "record {} cannot follow record {}",
                record.sequence,
                expected - 1
            )));
        }

        let bytes: Vec<u8> = records
            .iter()
            .flat_map(Record::encode)
            .collect();

        if let Err(error) = self.write(&bytes) {
            self.failed = true;

            return Err(error);
        }

        self.next += records.len() as u64;

        Ok(())
    }
}

The leader

A leader has 3 responsibilities: to accept writes, to send each follower whatever records it lacks, and to determine which records are committed.

Proposing a record

propose checks the condition of a write against the entries and appends the record to the leader’s own log. The record is not yet applied, since at this point only 1 replica holds it.

A leader accepts a new write only when is_settled is true, which is to say when every record in its log is committed. The reason lies in conditional writes. A condition is checked against the entries, and the entries do not include uncommitted records. If the leader were to accept a second write while an earlier record was still uncommitted, the condition of the second would be evaluated against a state that lacked its predecessor, and a conditional write could succeed when it ought to have failed. Requiring a settled log guarantees that every condition is evaluated against all earlier writes. The price is that the writes of a shard are processed strictly in sequence. Production systems evaluate conditions against a speculative state and process writes in batches, which is considerably more intricate and is not attempted here, although chapter 6 recovers much of the lost throughput by another means.

Within propose, the present version of the key is read from the entries, a Delete of a key that does not exist is rejected, and check evaluates the condition. Only then is the record appended. On return, the record is in the leader’s log and in records, and the entries are unchanged.

Listing 3.8 Checking the condition of a write and appending its record. repl/src/lib.rs

impl Replica {
    /// Whether every record of the log is committed. A leader accepts a new
    /// write only in this state, so that the condition of the write is
    /// checked against the result of all earlier writes.
    pub fn is_settled(&self) -> bool {
        self.committed == self.last_sequence()
    }

    /// Checks the condition of a write and appends its record to the
    /// leader's log. The record is not applied: it is not committed yet.
    pub fn propose(&mut self, change: Change, condition: Condition) -> Result<u64, StoreError> {
        let key = match &change {
            Change::Put { key, .. } | Change::Delete { key } => key,
        };
        let current = self
            .entries
            .get(key)
            .map(|entry| entry.version);

        if matches!(change, Change::Delete { .. }) && current.is_none() {
            return Err(StoreError::NotFound);
        }

        check(condition, current)?;

        let record = self.log.append(change)?;
        let sequence = record.sequence;
        self.records.push(record);

        Ok(sequence)
    }
}

Building a message for a follower

For every follower, the leader remembers the last sequence that the follower reported. append_for takes that number and returns a message containing every later record. For a follower that is up to date, the slice of records is empty and the message is a heartbeat. A reported sequence that lies beyond the end of the leader’s own log is limited to that end, a situation that can arise when a leader has itself been replaced and restarted with a shorter log.

Listing 3.9 The message that brings 1 follower up to date. repl/src/lib.rs

impl Replica {
    /// The message that brings a follower whose log ends at `follower_last`
    /// up to the end of this log. With nothing to send it is a heartbeat.
    pub fn append_for(&self, follower_last: u64) -> Append {
        let from = follower_last.min(self.last_sequence()) as usize;

        Append {
            term: self.term,
            previous_sequence: from as u64,
            records: self.records[from..].to_vec(),
            committed_sequence: self.committed,
        }
    }
}

The commit rule

The leader knows where its own log ends and what last sequence each follower has reported. If these numbers are sorted, the one in the middle is the highest sequence that a majority has stored.

majority_sequence implements the rule for any number of replicas, by taking the element at index n / 2 of the values sorted in descending order. For 3 replicas that is the second value, and for 5 the third.

Listing 3.10 The commit rule. repl/src/lib.rs

/// The highest sequence that is stored on a majority, given the last
/// sequence of every replica, the leader included.
pub fn majority_sequence(mut last_sequences: Vec<u64>) -> u64 {
    last_sequences.sort_unstable_by(|a, b| b.cmp(a));

    last_sequences
        .get(last_sequences.len() / 2)
        .copied()
        .unwrap_or(0)
}

Simulating lost messages

Because the library performs no network operations, a test can carry the messages between replicas itself and decide the fate of every exchange. This is the reason for writing the rules as a library in the first place. Faults in a real network occur rarely and unrepeatably, and a protocol that has only been tested on a real network has scarcely been tested against faults at all.

replsim creates a leader and 2 followers in a single process. For each exchange it chooses 1 of 3 outcomes: the message is delivered and answered, the message is lost, or the message is processed and its answer is lost.

/// What happens to one exchange between the leader and a follower.
#[derive(Clone, Copy, PartialEq, Eq)]
enum Fate {
    Delivered,
    /// The follower does not receive the message.
    RequestLost,
    /// The follower processes the message, and its answer does not arrive.
    AnswerLost,
}

/// A leader, 2 followers, and what the leader knows about each follower.
struct Cluster {
    leader: Replica,
    followers: Vec<Replica>,
    /// The last sequence each follower has reported.
    reported: Vec<u64>,
}

impl Cluster {
    fn open(root: &Path) -> Result<Cluster, Box<dyn Error>> {
        let open = |name: &str| Replica::open(&root.join(name), false, 1);

        Ok(Cluster {
            leader: open("leader")?,
            followers: vec![open("follower-1")?, open("follower-2")?],
            reported: vec![0, 0],
        })
    }

    /// One exchange with a follower: the leader sends what the follower
    /// lacks, as far as it knows, and commits what a majority now holds.
    fn exchange(&mut self, follower: usize, fate: Fate) -> Result<(), Box<dyn Error>> {
        let message = self
            .leader
            .append_for(self.reported[follower]);

        if fate == Fate::RequestLost {
            return Ok(());
        }

        let answer = self.followers[follower].handle_append(message)?;

        if fate == Fate::AnswerLost {
            return Ok(());
        }

        self.reported[follower] = answer.last_sequence;

        let stored = vec![
            self.leader.last_sequence(),
            self.reported[0],
            self.reported[1],
        ];
        self.leader
            .commit(majority_sequence(stored));

        Ok(())
    }

    /// A write: the leader appends the record and makes one exchange with
    /// each follower. It returns whether the write was acknowledged, or
    /// `None` when the leader could not accept it.
    fn write(
        &mut self,
        key: &str,
        value: &str,
        fates: [Fate; 2],
    ) -> Result<Option<bool>, Box<dyn Error>> {
        if !self.leader.is_settled() {
            return Ok(None);
        }

        let change = Change::Put {
            key: key.into(),
            value: value.into(),
        };
        let sequence = self
            .leader
            .propose(change, Condition::Always)?;

        self.exchange(0, fates[0])?;
        self.exchange(1, fates[1])?;

        Ok(Some(self.leader.committed() >= sequence))
    }

    /// The last sequence of the leader and of each follower.
    fn lasts(&self) -> [u64; 3] {
        [
            self.leader.last_sequence(),
            self.followers[0].last_sequence(),
            self.followers[1].last_sequence(),
        ]
    }
}

The second part runs 3 writes under every combination of outcomes. Each write involves 2 exchanges, and each exchange is assigned 2 bits of a pattern, which gives 4096 patterns. After each pattern, replsim verifies invariants 1 and 2, then delivers all messages and verifies that the 3 logs become equal.

Listing 3.14 Every combination of lost messages over 3 writes. replsim/src/main.rs

const WRITES: usize = 3;

/// The fate of exchange number `index` under a pattern: 2 bits for each.
fn fate(pattern: u32, index: usize) -> Fate {
    match (pattern >> (2 * index)) & 3 {
        0 | 1 => Fate::Delivered,
        2 => Fate::RequestLost,
        3.. => Fate::AnswerLost,
    }
}

/// Runs 3 writes under one pattern of losses and checks the replicas. It
/// returns the number of writes that were acknowledged.
fn run(root: &Path, pattern: u32) -> Result<usize, Box<dyn Error>> {
    let mut cluster = Cluster::open(root)?;
    let mut acknowledged = Vec::new();

    for number in 0..WRITES {
        let fates = [fate(pattern, 2 * number), fate(pattern, 2 * number + 1)];

        if cluster.write(&format!("key-{number}"), "1", fates)? == Some(true) {
            acknowledged.push(cluster.leader.last_sequence());
        }
    }

    for &sequence in &acknowledged {
        let holders = cluster
            .lasts()
            .iter()
            .filter(|&&last| last >= sequence)
            .count();

        if holders < 2 {
            return Err(format!(
                "pattern {pattern}: record {sequence} was acknowledged and is in {holders} log"
            )
            .into());
        }
    }

    for follower in &cluster.followers {
        if !cluster
            .leader
            .records()
            .starts_with(follower.records())
        {
            return Err(format!(
                "pattern {pattern}: a follower's log is not the beginning of the leader's"
            )
            .into());
        }
    }

    for _ in 0..2 {
        cluster.exchange(0, Fate::Delivered)?;
        cluster.exchange(1, Fate::Delivered)?;
    }

    let [leader, first, second] = cluster.lasts();

    if first != leader || second != leader || !cluster.leader.is_settled() {
        return Err(format!(
            "pattern {pattern}: the logs differ after every message was delivered"
        )
        .into());
    }

    Ok(acknowledged.len())
}

fn exhaustive(root: &Path) -> Result<(), Box<dyn Error>> {
    let patterns = 1u32 << (4 * WRITES);
    let mut by_acknowledged = [0; WRITES + 1];

    for pattern in 0..patterns {
        let directory = root.join(format!("pattern-{pattern}"));
        by_acknowledged[run(&directory, pattern)?] += 1;
        fs::remove_dir_all(&directory)?;
    }

    println!("{patterns} patterns of lost messages over {WRITES} writes:");
    println!("  every acknowledged record was in at least 2 of the 3 logs");

        &self,
        request: Request<proto::AppendRequest>,

            .into_iter()
            .map(Record::try_from)

            previous_sequence: request.previous_sequence,
            records,

            appended: answer.appended,

A leader starts 1 task for each follower. The task repeats a single exchange: it builds a message that begins where the follower’s log is believed to end, sends it, and processes the answer. When the follower is up to date, the task waits until the leader appends a record or until the heartbeat interval has elapsed. When the answer shows that records are still missing, the task continues at once.

follow runs for the lifetime of the node, and its loop has 3 phases. It first locks the replica for no longer than it takes to build a message. It then releases the lock and waits for the answer, for at most 500 ms. Finally it passes the answer to record. If record reports that the follower is still behind, the loop continues immediately. Otherwise the task sleeps until appended is signalled or the heartbeat interval elapses, whichever occurs first.

Listing 3.25 The task that keeps a follower up to date. kvnode/src/node.rs

impl Node {
    /// Starts one task for each follower. A task sends the follower what it
    /// lacks, again and again, for as long as the node runs.
    pub fn lead(self: &Arc<Node>) -> Result<(), tonic::transport::Error> {
        for index in 0..self.peers.len() {
            let channel = Endpoint::from_shared(self.peers[index].address.clone())?
                .connect_timeout(ANSWER)
                .connect_lazy();

            tokio::spawn(Arc::clone(self).follow(index, ReplicationClient::new(channel)));
        }

        Ok(())
    }

    async fn follow(self: Arc<Node>, index: usize, mut client: ReplicationClient<Channel>) {
        let peer = &self.peers[index];

        loop {
            let message = self.replica.lock().append_for(
                peer.reported
                    .load(Ordering::Relaxed),
            );
            let request = proto::AppendRequest::from(message);

            let answer = timeout(ANSWER, client.append(request)).await;

            // An answer that did not come counts as a peer that is up to date:
            // the next round is a heartbeat, which finds out more.
            let behind = answer
                .ok()
                .and_then(Result::ok)
                .is_some_and(|answer| self.record(peer, answer.into_inner().into()));

            if !behind {
                // Wait for a new record, or send a heartbeat when none comes.
                tokio::select! {
                    () = self.appended.notified() => {}
                    () = sleep(HEARTBEAT) => {}
                }
            }
        }
    }
}

A point of design here has a large effect on how the node behaves under faults. No task holds the lock of the replica while it waits for the network. It takes the lock to build a message and again to process an answer, and releases it in between. An unreachable follower therefore delays its own task and nothing else, neither the task of the other follower nor any request from a client. Had the lock been held across the network call, a single slow follower would have stopped the whole shard, which would have defeated the purpose of waiting only for a majority.

record is called with every answer. It first compares the term of the answer with the leader’s own. A higher term shows that a newer leader exists, and the node ceases to accept writes. Otherwise it stores the sequence reported, applies the commit rule to the 3 last sequences, and publishes the new committed sequence through a watch channel, where the waiting writes observe it.

Listing 3.26 Processing an answer, and committing. kvnode/src/node.rs

impl Node {
    /// Takes note of a follower's answer and commits what a majority now
    /// holds. It returns whether the follower still lacks records.
    fn record(&self, peer: &Peer, answer: Appended) -> bool {
        let mut replica = self.replica.lock();

        if answer.term > replica.term() {
            self.deposed
                .store(true, Ordering::Relaxed);

            return false;
        }

        peer.reported
            .store(answer.last_sequence, Ordering::Relaxed);
        *peer.heard.lock() = Some(Instant::now());

        let mut stored: Vec<u64> = self
            .peers
            .iter()
            .map(|peer| {
                peer.reported
                    .load(Ordering::Relaxed)
            })
            .collect();
        stored.push(replica.last_sequence());

        replica.commit(majority_sequence(stored));
        self.committed
            .send_replace(replica.committed());

        answer.last_sequence < replica.last_sequence()
    }
}

Writes

Listing 3.27 The write path of the leader. kvnode/src/node.rs

impl Node {
    /// A write on the leader: wait for a turn, append the record, and wait
    /// until a majority of the replicas hold it.
    pub async fn write(&self, change: Change, condition: Condition) -> Result<Written, ApiError> {
        self.must_lead()?;

        let turn = self.turn.lock().await;
        let last = self.replica.lock().last_sequence();
        self.wait_for(last).await?;

        let proposed = task::block_in_place(|| {
            let mut replica = self.replica.lock();
            let created = match &change {
                Change::Put { key, .. } | Change::Delete { key } => replica.get(key).is_none(),
            };

            replica
                .propose(change, condition)
                .map(|version| Written { version, created })
        })?;

        self.appended.notify_waiters();
        self.wait_for(proposed.version)
            .await?;
        drop(turn);

        Ok(proposed)
    }

    /// Waits until the record with this sequence is committed.
    async fn wait_for(&self, sequence: u64) -> Result<(), ApiError> {
        let mut committed = self.committed.subscribe();

        let reached = committed.wait_for(|&committed| committed >= sequence);
        let in_time = timeout(COMMIT, reached)
            .await
            .is_ok_and(|reached| reached.is_ok());

        if in_time {
            Ok(())
        } else {
            Err(ApiError::Unavailable(format!(
                "record {sequence} is not on a majority of the replicas"
            )))
        }
    }

    fn must_lead(&self) -> Result<(), ApiError> {
        if !self.leader {
            return Err(ApiError::Misdirected("this node is a follower".into()));
        }

        if self.deposed.load(Ordering::Relaxed) {
            return Err(ApiError::Misdirected(
                "a leader of a newer term exists".into(),
            ));
        }

        Ok(())
    }
}

The handlers send no messages themselves. A handler appends a record, wakes both follower tasks, and waits for the committed sequence to reach the sequence of its record. A watch channel holds the most recent committed sequence, and wait_for returns as soon as that value satisfies its condition, including the case in which it already does.

If no majority stores the record within 1 second, the handler answers 503. The record remains in the leader’s log. The follower tasks go on sending it, and it is committed when a follower becomes reachable, as the simulation showed.

Reads

Listing 3.28 The read path of the leader. kvnode/src/node.rs

impl Node {
    /// A leader serves reads while a majority of the replicas, itself
    /// included, has answered within the last second, and once everything
    /// its log held at start is committed.
    fn must_serve_reads(&self) -> Result<(), ApiError> {
        self.must_lead()?;

        let recently = |peer: &&Peer| {
            peer.heard
                .lock()
                .is_some_and(|at| at.elapsed() < COMMIT)
        };
        let reachable = 1 + self
            .peers
            .iter()
            .filter(recently)
            .count();

        if 2 * reachable <= self.peers.len() + 1 {
            return Err(ApiError::Unavailable(
                "this leader cannot reach a majority of the replicas".into(),
            ));
        }

        if self.replica.lock().committed() < self.ready {
            return Err(ApiError::Unavailable(
                "the records from before the restart are not committed yet".into(),
            ));
        }

        Ok(())
    }

    pub fn get(&self, key: &str) -> Result<Entry, ApiError> {
        self.must_serve_reads()?;

        self.replica
            .lock()
            .get(key)
            .cloned()
            .ok_or(ApiError::NotFound)
    }

    pub fn list(
        &self,
        prefix: &str,
        after: Option<&str>,
        limit: usize,
    ) -> Result<(Vec<Summary>, bool), ApiError> {
        self.must_serve_reads()?;

        Ok(self
            .replica
            .lock()
            .list(prefix, after, limit))
    }

    /// The last sequence each follower has reported.
    pub fn reported(&self) -> Vec<u64> {
        self.peers
            .iter()
            .map(|peer| {
                peer.reported
                    .load(Ordering::Relaxed)
            })
            .collect()
    }
}

A leader that has been separated from its followers by a network partition cannot know whether another leader has been appointed in the meantime, and its entries may therefore be out of date. must_serve_reads accordingly requires that a majority of the replicas, counting the leader itself, has answered within the last second. The check limits to 1 second the time for which a former leader could return outdated data, on the condition that no new leader is appointed sooner than that after the old one becomes unreachable. Stricter implementations confirm their leadership with a majority for every read, at the cost of a network round trip for each.

A second check concerns a leader that has been restarted. Its log may contain committed records that have not yet been applied, since committed begins at 0. Such a leader serves reads once every record that its log held at startup has been committed again.

Limitations

LimitationConsequence
The leader is appointed by an operator.After the loss of a leader, the shard is unavailable for writes until a person or a script promotes a follower.
A former leader must not rejoin with its old log.Its log may contain records that were appended and never committed, at positions where the new leader has written different records. The implementation compares positions only, so a former leader has to rejoin with an empty data directory.
Writes are processed 1 after another.The write rate of a shard is limited to 1 write for each round trip. Group commit, which the capacity estimate of chapter 1 assumed, is not implemented.
Every replica holds all its records in memory.The memory used by a node grows with the length of its log.
A leader serves reads for up to 1 second after losing its majority.Non-functional requirement 2, consistency, depends on no new leader being appointed within that second.

The first 2 limitations are removed in chapter 4, and the third in chapter 6.

//! Replication of a log from a leader to its followers.
//!
//! A `Replica` is one copy of a shard: a log, and the entries that result
//! from the records that are known to be on a majority of the copies. The
//! same type serves as leader and as follower. This module does no I/O on
//! the network. It builds the messages and processes them, and the caller
//! carries them between replicas.

use std::collections::BTreeMap;
use std::io;
use std::path::Path;

use kv::{Change, Condition, Entry, Log, Record, StoreError, Summary, apply, check, page};

/// The message a leader sends to a follower.
#[derive(Debug, Clone, PartialEq, Eq)]
pub struct Append {
    /// The term of the sender.
    pub term: u64,
    /// The sequence of the record that precedes `records` in the leader's log.
    pub previous_sequence: u64,
    pub records: Vec<Record>,
    /// Every record up to this sequence is on a majority of the replicas.
    pub committed_sequence: u64,
}

/// The follower's answer.
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub struct Appended {
    pub term: u64,
    /// False when the follower's log does not end at `previous_sequence`,
    /// or when the sender's term is older than the follower's.
    pub appended: bool,
    /// The sequence of the last record in the follower's log.
    pub last_sequence: u64,
}

pub struct Replica {
    log: Log,
    /// Every record of the log, in order. Record `n` is at index `n - 1`.
    records: Vec<Record>,
    /// The result of applying the records up to `committed`.
    entries: BTreeMap<String, Entry>,
    /// The sequence of the last record that is applied to `entries`.
    committed: u64,
    term: u64,
}

impl Replica {
    /// Opens the replica in `directory`. Nothing is applied yet: a replica
    /// that has restarted does not know which of its records are committed.
    pub fn open(directory: &Path, sync: bool, term: u64) -> io::Result<Replica> {
        let (log, recovery) = Log::open(directory, sync)?;

        Ok(Replica {
            log,
            records: recovery.records,
            entries: BTreeMap::new(),
            committed: 0,
            term,
        })
    }

    pub fn term(&self) -> u64 {
        self.term
    }

    pub fn last_sequence(&self) -> u64 {
        self.records.len() as u64
    }

    pub fn committed(&self) -> u64 {
        self.committed
    }

    /// One page of the committed keys.
    pub fn list(&self, prefix: &str, after: Option<&str>, limit: usize) -> (Vec<Summary>, bool) {
        page(&self.entries, prefix, after, limit)
    }

    /// Every record of the log, in order.
    pub fn records(&self) -> &[Record] {
        &self.records
    }

    /// The committed value of a key.
    pub fn get(&self, key: &str) -> Option<&Entry> {
        self.entries.get(key)
    }

    /// Applies the records up to `sequence` that are not applied yet.
    pub fn commit(&mut self, sequence: u64) {
        let until = sequence.min(self.last_sequence());

        while self.committed < until {
            apply(
                &mut self.entries,
                self.records[self.committed as usize].clone(),
            );
            self.committed += 1;
        }
    }
}

impl Replica {
    /// Whether every record of the log is committed. A leader accepts a new
    /// write only in this state, so that the condition of the write is
    /// checked against the result of all earlier writes.
    pub fn is_settled(&self) -> bool {
        self.committed == self.last_sequence()
    }

    /// Checks the condition of a write and appends its record to the
    /// leader's log. The record is not applied: it is not committed yet.
    pub fn propose(&mut self, change: Change, condition: Condition) -> Result<u64, StoreError> {
        let key = match &change {
            Change::Put { key, .. } | Change::Delete { key } => key,
        };
        let current = self
            .entries
            .get(key)
            .map(|entry| entry.version);

        if matches!(change, Change::Delete { .. }) && current.is_none() {
            return Err(StoreError::NotFound);
        }

        check(condition, current)?;

        let record = self.log.append(change)?;
        let sequence = record.sequence;
        self.records.push(record);

        Ok(sequence)
    }
}

impl Replica {
    /// The message that brings a follower whose log ends at `follower_last`
    /// up to the end of this log. With nothing to send it is a heartbeat.
    pub fn append_for(&self, follower_last: u64) -> Append {
        let from = follower_last.min(self.last_sequence()) as usize;

        Append {
            term: self.term,
            previous_sequence: from as u64,
            records: self.records[from..].to_vec(),
            committed_sequence: self.committed,
        }
    }
}


/// The highest sequence that is stored on a majority, given the last
/// sequence of every replica, the leader included.
pub fn majority_sequence(mut last_sequences: Vec<u64>) -> u64 {
    last_sequences.sort_unstable_by(|a, b| b.cmp(a));

    last_sequences
        .get(last_sequences.len() / 2)
        .copied()
        .unwrap_or(0)
}

impl Replica {
    /// Processes a message from a leader.
    pub fn handle_append(&mut self, request: Append) -> io::Result<Appended> {
        let refuse = |replica: &Replica| Appended {
            term: replica.term,
            appended: false,
            last_sequence: replica.last_sequence(),
        };

        if request.term < self.term {
            return Ok(refuse(self));
        }

        self.term = request.term;

        if request.previous_sequence != self.last_sequence() {
            return Ok(refuse(self));
        }

        if !request.records.is_empty() {
            self.log
                .append_records(&request.records)?;
            self.records.extend(request.records);
        }

        self.commit(request.committed_sequence);

        Ok(Appended {
            term: self.term,
            appended: true,
            last_sequence: self.last_sequence(),
        })
    }
}

//! Command replsim runs a leader and 2 followers in one process and carries
//! the messages between them by hand, so that it can lose any message it
//! chooses. It first walks through the cases of the chapter, and then tries
//! every combination of lost requests and lost answers over 3 writes and
//! checks what the replicas hold after each.
//!
//! Run it from code/ with:
//!
//!     cargo run --release -p replsim

use std::env;
use std::error::Error;
use std::fs;
use std::path::{Path, PathBuf};
use std::process;

use kv::{Change, Condition};
use repl::{Replica, majority_sequence};

/// What happens to one exchange between the leader and a follower.
#[derive(Clone, Copy, PartialEq, Eq)]
enum Fate {
    Delivered,
    /// The follower does not receive the message.
    RequestLost,
    /// The follower processes the message, and its answer does not arrive.
    AnswerLost,
}

/// A leader, 2 followers, and what the leader knows about each follower.
struct Cluster {
    leader: Replica,
    followers: Vec<Replica>,
    /// The last sequence each follower has reported.
    reported: Vec<u64>,
}

impl Cluster {
    fn open(root: &Path) -> Result<Cluster, Box<dyn Error>> {
        let open = |name: &str| Replica::open(&root.join(name), false, 1);

        Ok(Cluster {
            leader: open("leader")?,
            followers: vec![open("follower-1")?, open("follower-2")?],
            reported: vec![0, 0],
        })
    }

    /// One exchange with a follower: the leader sends what the follower
    /// lacks, as far as it knows, and commits what a majority now holds.
    fn exchange(&mut self, follower: usize, fate: Fate) -> Result<(), Box<dyn Error>> {
        let message = self
            .leader
            .append_for(self.reported[follower]);

        if fate == Fate::RequestLost {
            return Ok(());
        }

        let answer = self.followers[follower].handle_append(message)?;

        if fate == Fate::AnswerLost {
            return Ok(());
        }

        self.reported[follower] = answer.last_sequence;

        let stored = vec![
            self.leader.last_sequence(),
            self.reported[0],
            self.reported[1],
        ];
        self.leader
            .commit(majority_sequence(stored));

        Ok(())
    }

    /// A write: the leader appends the record and makes one exchange with
    /// each follower. It returns whether the write was acknowledged, or
    /// `None` when the leader could not accept it.
    fn write(
        &mut self,
        key: &str,
        value: &str,
        fates: [Fate; 2],
    ) -> Result<Option<bool>, Box<dyn Error>> {
        if !self.leader.is_settled() {
            return Ok(None);
        }

        let change = Change::Put {
            key: key.into(),
            value: value.into(),
        };
        let sequence = self
            .leader
            .propose(change, Condition::Always)?;

        self.exchange(0, fates[0])?;
        self.exchange(1, fates[1])?;

        Ok(Some(self.leader.committed() >= sequence))
    }

    /// The last sequence of the leader and of each follower.
    fn lasts(&self) -> [u64; 3] {
        [
            self.leader.last_sequence(),
            self.followers[0].last_sequence(),
            self.followers[1].last_sequence(),
        ]
    }
}

const BOTH: [Fate; 2] = [Fate::Delivered, Fate::Delivered];

const WRITES: usize = 3;

/// The fate of exchange number `index` under a pattern: 2 bits for each.
fn fate(pattern: u32, index: usize) -> Fate {
    match (pattern >> (2 * index)) & 3 {
        0 | 1 => Fate::Delivered,
        2 => Fate::RequestLost,
        3.. => Fate::AnswerLost,
    }
}

/// Runs 3 writes under one pattern of losses and checks the replicas. It
/// returns the number of writes that were acknowledged.
fn run(root: &Path, pattern: u32) -> Result<usize, Box<dyn Error>> {
    let mut cluster = Cluster::open(root)?;
    let mut acknowledged = Vec::new();

    for number in 0..WRITES {
        let fates = [fate(pattern, 2 * number), fate(pattern, 2 * number + 1)];

        if cluster.write(&format!("key-{number}"), "1", fates)? == Some(true) {
            acknowledged.push(cluster.leader.last_sequence());
        }
    }

    for &sequence in &acknowledged {
        let holders = cluster
            .lasts()
            .iter()
            .filter(|&&last| last >= sequence)
            .count();

        if holders < 2 {
            return Err(format!(
                "pattern {pattern}: record {sequence} was acknowledged and is in {holders} log"
            )
            .into());
        }
    }

    for follower in &cluster.followers {
        if !cluster
            .leader
            .records()
            .starts_with(follower.records())
        {
            return Err(format!(
                "pattern {pattern}: a follower's log is not the beginning of the leader's"
            )
            .into());
        }
    }

    for _ in 0..2 {
        cluster.exchange(0, Fate::Delivered)?;
        cluster.exchange(1, Fate::Delivered)?;
    }

    let [leader, first, second] = cluster.lasts();

    if first != leader || second != leader || !cluster.leader.is_settled() {
        return Err(format!(
            "pattern {pattern}: the logs differ after every message was delivered"
        )
        .into());
    }

    Ok(acknowledged.len())
}

fn exhaustive(root: &Path) -> Result<(), Box<dyn Error>> {
    let patterns = 1u32 << (4 * WRITES);
    let mut by_acknowledged = [0; WRITES + 1];

    for pattern in 0..patterns {
        let directory = root.join(format!("pattern-{pattern}"));
        by_acknowledged[run(&directory, pattern)?] += 1;
        fs::remove_dir_all(&directory)?;
    }

    println!("{patterns} patterns of lost messages over {WRITES} writes:");
    println!("  every acknowledged record was in at least 2 of the 3 logs");
    println!("  every follower's log was the beginning of the leader's log");
    println!("  after the losses stopped, the 3 logs were equal and every record was committed");

    for (count, patterns) in by_acknowledged.iter().enumerate() {
        println!("  {count} of {WRITES} writes acknowledged: {patterns} patterns");
    }

    Ok(())
}

fn directory() -> PathBuf {
    env::temp_dir().join(format!("replsim-{}", process::id()))
}

fn main() -> Result<(), Box<dyn Error>> {
    let root = directory();
    let result = cases(&root.join("cases")).and_then(|()| exhaustive(&root));

    fs::remove_dir_all(&root)?;

    result
}

//! The replication service: the generated gRPC types, the conversion between
//! them and the types of the `repl` crate, and the server side that a

use std::sync::Arc;

use kv::{Change, Record};

use tonic::{Request, Response, Status};

use crate::node::Node;

/// The types that `build.rs` generates from `proto/store.proto`. The schema
/// also defines the ring, which this program does not use.
#[allow(dead_code)]
pub mod proto {
    tonic::include_proto!("store.v1");
}

pub use proto::replication_client::ReplicationClient;
pub use proto::replication_server::{Replication, ReplicationServer};

impl From<&Record> for proto::Record {
    fn from(record: &Record) -> Self {
        let change = match record.change.clone() {
            Change::Put { key, value } => proto::record::Change::Put(proto::Put { key, value }),
            Change::Delete { key } => proto::record::Change::Delete(proto::Delete { key }),
        };

        proto::Record {
            sequence: record.sequence,
            change: Some(change),
        }
    }
}

impl TryFrom<proto::Record> for Record {
    type Error = Status;

    fn try_from(record: proto::Record) -> Result<Self, Status> {
        let change = match record.change {
            Some(proto::record::Change::Put(put)) => Change::Put {
                key: put.key,
                value: put.value,
            },
            Some(proto::record::Change::Delete(delete)) => Change::Delete { key: delete.key },
            None => return Err(Status::invalid_argument("a record without a change")),
        };

        Ok(Record {
            sequence: record.sequence,
            change,
        })
    }
}

impl From<Append> for proto::AppendRequest {
    fn from(message: Append) -> Self {
        proto::AppendRequest {
            shard: 0,
            term: message.term,
            previous_sequence: message.previous_sequence,
            records: message
                .records
                .iter()
                .map(proto::Record::from)
                .collect(),
            committed_sequence: message.committed_sequence,
            // The fields that leader election added are not used by this program.
            previous_term: 0,
            leader: 0,
        }
    }
}

impl From<proto::AppendResponse> for Appended {
    fn from(answer: proto::AppendResponse) -> Self {
        Appended {
            term: answer.term,
            appended: answer.appended,
            last_sequence: answer.last_sequence,
        }
    }
}

/// The server side of `Append`, which a follower runs.
pub struct Follower {
    pub node: Arc<Node>,
}

#[tonic::async_trait]
impl Replication for Follower {
    async fn append(
        &self,
        request: Request<proto::AppendRequest>,
    ) -> Result<Response<proto::AppendResponse>, Status> {
        let request = request.into_inner();
        let records = request
            .records
            .into_iter()
            .map(Record::try_from)
            .collect::<Result<Vec<_>, _>>()?;

        let message = Append {
            term: request.term,
            previous_sequence: request.previous_sequence,
            records,
            committed_sequence: request.committed_sequence,
        };

        // Appending waits for the disk, so it runs where blocking is allowed.
        let answer = task::block_in_place(|| {
            self.node
                .replica
                .lock()
                .handle_append(message)
        })
        .map_err(|error| Status::unavailable(error.to_string()))?;

        Ok(Response::new(proto::AppendResponse {
            term: answer.term,
            appended: answer.appended,
            last_sequence: answer.last_sequence,
        }))
    }
}

//! A node of a replicated shard: a replica, and for a leader the tasks that
//! keep its followers up to date.

use std::sync::Arc;
use std::sync::atomic::{AtomicBool, AtomicU64, Ordering};
use std::time::{Duration, Instant};

use kv::{Change, Condition, Entry, Summary, Written};
use kvd::api::ApiError;
use parking_lot::Mutex;
use repl::{Appended, Replica, majority_sequence};
use tokio::sync::{Notify, watch};
use tokio::task;
use tokio::time::{sleep, timeout};
use tonic::transport::{Channel, Endpoint};

use crate::rpc::{ReplicationClient, proto};

/// How often a leader sends a message to a follower that has nothing new to receive.
const HEARTBEAT: Duration = Duration::from_millis(100);

/// How long a leader waits for the answer to one message.
const ANSWER: Duration = Duration::from_millis(500);

/// How long a write waits for its record to reach a majority.
const COMMIT: Duration = Duration::from_secs(1);

/// What the leader knows about one follower.
pub struct Peer {
    pub address: String,
    /// The last sequence the follower has reported.
    reported: AtomicU64,
    /// When the follower last answered.
    heard: Mutex<Option<Instant>>,
}

pub struct Node {
    pub replica: Mutex<Replica>,
    pub leader: bool,
    pub peers: Vec<Peer>,
    /// The sequence the log ended at when the node started. A leader serves
    /// reads once this much is committed.
    ready: u64,
    /// Held by the write that is in progress, so that writes take turns.
    turn: tokio::sync::Mutex<()>,
    /// The committed sequence, for writes that wait for it to advance.
    committed: watch::Sender<u64>,
    /// Signalled when the leader has appended a record.
    appended: Notify,
    /// Set when a follower answers with a newer term: another leader exists.
    deposed: AtomicBool,
}

impl Node {
    pub fn new(replica: Replica, leader: bool, followers: Vec<String>) -> Arc<Node> {
        let peer = |address| Peer {
            address,
            reported: AtomicU64::new(0),
            heard: Mutex::new(None),
        };

        Arc::new(Node {
            ready: replica.last_sequence(),
            replica: Mutex::new(replica),
            leader,
            peers: followers
                .into_iter()
                .map(peer)
                .collect(),
            turn: tokio::sync::Mutex::new(()),
            committed: watch::Sender::new(0),
            appended: Notify::new(),
            deposed: AtomicBool::new(false),
        })
    }
}

impl Node {
    /// Starts one task for each follower. A task sends the follower what it
    /// lacks, again and again, for as long as the node runs.
    pub fn lead(self: &Arc<Node>) -> Result<(), tonic::transport::Error> {
        for index in 0..self.peers.len() {
            let channel = Endpoint::from_shared(self.peers[index].address.clone())?
                .connect_timeout(ANSWER)
                .connect_lazy();

            tokio::spawn(Arc::clone(self).follow(index, ReplicationClient::new(channel)));
        }

        Ok(())
    }

    async fn follow(self: Arc<Node>, index: usize, mut client: ReplicationClient<Channel>) {
        let peer = &self.peers[index];

        loop {
            let message = self.replica.lock().append_for(
                peer.reported
                    .load(Ordering::Relaxed),
            );
            let request = proto::AppendRequest::from(message);

            let answer = timeout(ANSWER, client.append(request)).await;

            // An answer that did not come counts as a peer that is up to date:
            // the next round is a heartbeat, which finds out more.
            let behind = answer
                .ok()
                .and_then(Result::ok)
                .is_some_and(|answer| self.record(peer, answer.into_inner().into()));

            if !behind {
                // Wait for a new record, or send a heartbeat when none comes.
                tokio::select! {
                    () = self.appended.notified() => {}
                    () = sleep(HEARTBEAT) => {}
                }
            }
        }
    }
}

impl Node {
    /// Takes note of a follower's answer and commits what a majority now
    /// holds. It returns whether the follower still lacks records.
    fn record(&self, peer: &Peer, answer: Appended) -> bool {
        let mut replica = self.replica.lock();

        if answer.term > replica.term() {
            self.deposed
                .store(true, Ordering::Relaxed);

            return false;
        }

        peer.reported
            .store(answer.last_sequence, Ordering::Relaxed);
        *peer.heard.lock() = Some(Instant::now());

        let mut stored: Vec<u64> = self
            .peers
            .iter()
            .map(|peer| {
                peer.reported
                    .load(Ordering::Relaxed)
            })
            .collect();
        stored.push(replica.last_sequence());

        replica.commit(majority_sequence(stored));
        self.committed
            .send_replace(replica.committed());

        answer.last_sequence < replica.last_sequence()
    }
}

impl Node {
    /// A write on the leader: wait for a turn, append the record, and wait
    /// until a majority of the replicas hold it.
    pub async fn write(&self, change: Change, condition: Condition) -> Result<Written, ApiError> {
        self.must_lead()?;

        let turn = self.turn.lock().await;
        let last = self.replica.lock().last_sequence();
        self.wait_for(last).await?;

        let proposed = task::block_in_place(|| {
            let mut replica = self.replica.lock();
            let created = match &change {
                Change::Put { key, .. } | Change::Delete { key } => replica.get(key).is_none(),
            };

            replica
                .propose(change, condition)
                .map(|version| Written { version, created })
        })?;

        self.appended.notify_waiters();
        self.wait_for(proposed.version)
            .await?;
        drop(turn);

        Ok(proposed)
    }

    /// Waits until the record with this sequence is committed.
    async fn wait_for(&self, sequence: u64) -> Result<(), ApiError> {
        let mut committed = self.committed.subscribe();

        let reached = committed.wait_for(|&committed| committed >= sequence);
        let in_time = timeout(COMMIT, reached)
            .await
            .is_ok_and(|reached| reached.is_ok());

        if in_time {
            Ok(())
        } else {
            Err(ApiError::Unavailable(format!(
                "record {sequence} is not on a majority of the replicas"
            )))
        }
    }

    fn must_lead(&self) -> Result<(), ApiError> {
        if !self.leader {
            return Err(ApiError::Misdirected("this node is a follower".into()));
        }

        if self.deposed.load(Ordering::Relaxed) {
            return Err(ApiError::Misdirected(
                "a leader of a newer term exists".into(),
            ));
        }

        Ok(())
    }
}

impl Node {
    /// A leader serves reads while a majority of the replicas, itself
    /// included, has answered within the last second, and once everything
    /// its log held at start is committed.
    fn must_serve_reads(&self) -> Result<(), ApiError> {
        self.must_lead()?;

        let recently = |peer: &&Peer| {
            peer.heard
                .lock()
                .is_some_and(|at| at.elapsed() < COMMIT)
        };
        let reachable = 1 + self
            .peers
            .iter()
            .filter(recently)
            .count();

        if 2 * reachable <= self.peers.len() + 1 {
            return Err(ApiError::Unavailable(
                "this leader cannot reach a majority of the replicas".into(),
            ));
        }

        if self.replica.lock().committed() < self.ready {
            return Err(ApiError::Unavailable(
                "the records from before the restart are not committed yet".into(),
            ));
        }

        Ok(())
    }

    pub fn get(&self, key: &str) -> Result<Entry, ApiError> {
        self.must_serve_reads()?;

        self.replica
            .lock()
            .get(key)
            .cloned()
            .ok_or(ApiError::NotFound)
    }

    pub fn list(
        &self,
        prefix: &str,
        after: Option<&str>,
        limit: usize,
    ) -> Result<(Vec<Summary>, bool), ApiError> {
        self.must_serve_reads()?;

        Ok(self
            .replica
            .lock()
            .list(prefix, after, limit))
    }

    /// The last sequence each follower has reported.
    pub fn reported(&self) -> Vec<u64> {
        self.peers
            .iter()
            .map(|peer| {
                peer.reported
                    .load(Ordering::Relaxed)
            })
            .collect()
    }
}

async fn put_key(
    State(node): State<Arc<Node>>,
    Path(key): Path<String>,
    headers: HeaderMap,
    body: Bytes,
) -> Result<Response, ApiError> {
    valid_key(&key)?;
    let condition = write_condition(&headers)?;

    let written = node
        .write(
            Change::Put {
                key,
                value: body.to_vec(),
            },
            condition,
        )
        .await?;
    let status = if written.created {
        StatusCode::CREATED
    } else {
        StatusCode::NO_CONTENT
    };

    Ok((status, [(ETAG, etag(written.version))]).into_response())
}

async fn delete_key(
    State(node): State<Arc<Node>>,
    Path(key): Path<String>,
    headers: HeaderMap,
) -> Result<StatusCode, ApiError> {
    valid_key(&key)?;
    let condition = write_condition(&headers)?;

    node.write(Change::Delete { key }, condition)
        .await?;

    Ok(StatusCode::NO_CONTENT)
}

async fn get_key(
    State(node): State<Arc<Node>>,
    Path(key): Path<String>,
    headers: HeaderMap,
) -> Result<Response, ApiError> {
    valid_key(&key)?;
    let cached = version_header(&headers, IF_NONE_MATCH)?;
    let entry = node.get(&key)?;
    let tag = [(ETAG, etag(entry.version))];

    if cached == Some(Condition::Version(entry.version)) {
        return Ok((StatusCode::NOT_MODIFIED, tag).into_response());
    }

    Ok((
        tag,
        [(CONTENT_TYPE, "application/octet-stream")],
        entry.value,
    )
        .into_response())
}

Summary

  • The leader of a shard sends each follower the records it lacks, in an Append message that states the position at which those records begin.
  • A follower appends only if its log ends at that position, and otherwise reports where its log ends, upon which the leader continues from there. This 1 rule deals with restarted followers, lost messages, lost answers and empty followers.
  • A record is committed when a majority of the replicas has stored it, and the leader computes the committed sequence as the middle value of the sorted last sequences.
  • A replica applies committed records only, so that no read returns data which could be lost with 1 machine.
  • A write that was answered with an error may still be committed later, and a client has to treat an error as an unknown outcome.
  • For 4096 combinations of lost messages and answers, the simulation verified that every acknowledged record was held in at least 2 of the 3 logs.
  • With 3 nodes on 1 disk, the replicated shard completed 77 writes per second, against 185 for a single node.
  • After the loss of a leader and its disk, promoting the follower with the longer log preserved all 228 acknowledged writes.
  • A term identifies the current leader, and followers refuse messages with a lower term, so that a replaced leader cannot modify its shard.
